# 直接执行器与精化：验收结论

**结论：相同算法改成直接执行，确实大幅降低了本轮 `lean --run` 后端的开销；这不意味着比较次数最少的策略就最快。** 按 run 数平衡取得了较好的总体结果，长度策略仍有明确负结果。没有更换扫描规则、规划器、合并树、Hybrid-8 阈值或固定四段方案，没有训练模型。

分支：`experiment/direct-executor`。从带全部历史未提交实验的工作区建立，HEAD/main 保持 `086c581604b626101006b9dbfaa1e78e26247afa`。未 commit、未 push，未删文件。开始时的 **354 个原有文件逐文件 SHA-256 核对未变**，其他 worktree 未动。新增范围仅为 `Algorithm/Direct/`、`Semantics/Direct.lean`、`Verification/Direct/` 和本实验目录；原有实验及负结果保留。

## 1. 已形式化证明

不是仅证明“最后都排好了”。同一泛型递归算法体分别以 Program、TimeM、Id 解释：

- `Symbolic.lean` 证明符号实例与旧实现的整个比较决策树相等，包含比较参数、check/sort 阶段和分支。
- `Morphism.lean` 证明解释与纯值、bind、比较以及各个递归构件交换。
- `Refinement.lean` 证明直接扫描产生完全相同的 runs 和计数；直接 merge、任意同一合并树的输出与计数相等；两种动态策略和所有已有静态 Schema 端到端精化。
- `execution_iff` 给无计数体的**同体符号插桩操作语义**唯一确定输出与成本。不用“输出相等”冒充“比较成本相等”。直接部署不执行这个符号程序。
- 通过精化迁移有序性、排列保持、按 run 数的 `C ≤ (n−1) + n * Nat.clog 2 r`、结构敏感渐近界与全输入 `O(n log n)`、全有序输入精确 `n−1` 次比较，以及长度策略的扫描加实际树预算界。Nat 减法截断，空输入和 r=0 已包含；没有把 r 当常数。
- 分阶段消融也证明等于旧执行结果和计数；check/sort 分项插桩与旧分项计数相等。轻量运行诊断中的上界另有定理证明等于原证书上界。

这些都是任意有限 `List α`、合法 `LinearOrder α` 下的通用结论。11 个新增模块隔离重新编译，32 条入口定理的公理依赖仅为 `propext`、`Quot.sound`、`Classical.choice`，没有 `sorry`、`admit`、自定义公理或 `native_decide` 证书。

只证明**键上的 ≤ 比较**。长度算术、List 遍历/构造/分配、规划器运行、输出消费和机器时间没有成本定理；没有宣称空间复杂度或编译器正确性。

## 3. 同等优化后，动态策略是否占优？

确认集 C 后端：run 数平衡比 Merge 少用 **28.4%** 时间，比固定四段少 **18.2%**；相对 Hybrid-8 只少 **3.6%**，逐输入胜出 55/90。三个种子分组的总体方向一致，但这仍是小幅、单机、该数据混合下的优势，不作统计显著性或通用最优声明。

长度策略的比较数最低，却比 Merge **慢 12.9%**、比 Hybrid-8 **慢 52.0%**、比 run 数平衡慢约 57.7%。比较次数优势仍没有普遍转化为耗时优势。

形态差异没有隐藏（完整表在 `summary.zh.md`）：

- 全有序、长 runs、不等长 runs：动态策略明显受益；全有序确认输入 C 总时间约 0.296/0.303 ms，Merge 1.125 ms、Hybrid-8 0.706 ms、固定四段 0.374 ms。
- 逆序：仍只识别非递减 runs，真实 r=n。run 数平衡为 1.470 ms，长度策略为 3.913 ms，Hybrid-8 为 1.035 ms；两种动态策略都退化。
- 随机、重复值、大量短 runs：run 数平衡未胜过 Hybrid-8；长度策略更差。没有增加下降 run 识别来“修好”这些测试成绩。

长度策略是上一阶段的 eager ascending-run Peeksort 切分规则移植，不是原版优化实现。本轮不据此声称超过现有自适应排序。

## 4. 消融能解释什么？

确认集端到端 ms：

| 策略 | 双旧、分阶段 | 只换扫描 | 只换合并执行 | 双直接、分阶段 | 完整直接计数 |
|---|---:|---:|---:|---:|---:|
| run 数平衡 | 604.653 | 375.479 | 265.066 | 34.819 | 35.005 |
| 长度策略 | 583.667 | 353.602 | 269.627 | 39.295 | 39.573 |

双旧分阶段与原 A 只差约 0.3%–0.5%；**仅拆掉最外层阶段组合不是主要收益**。以双旧分阶段为控制，只换扫描少约 38%–39% 时间，只换合并执行少约 54%–56%。两部分都有重要贡献，不能笼统归因于扫描或某一种闭包。各列都是实际端到端测量，不把独立重放相加。

B→C 在两种动态策略分别再减少约 72.3%、61.4% 时间。这个差异包含 TimeM 记录/累加、bind 与特化效果，不能解释为单独一次整数自增的价格。

源码中的 C 是 Id 实例，不调用 counted 再取 `.ret`。编译审计同时检查通用包装和实际 Nat 特化：通用实现仍含 Monad 字典/闭包；生成 C 的 23 个 plain 特化函数体没有 TimeM、比较 Program、动态 apply 或闭包分配，实际 merge 使用直接 Nat 比较和递归。共享空数组常量的名称不代表调用计数代码，审计检查了其初始化内容。

所有计时仍是同一个 `lean --run` 后端，**没有原生 C 成绩**。生成 C 只用于结构审计，不证明运行时零分配，也不证明编译器正确。没有把切换编译后端当作算法加速。

## 5. 扩展与资源边界

统一扩展预算：每个请求 5 秒（一次预热加三轮、核对和返回；不是单次排序上界），总预算 180 秒，OS 栈软限制 8 MiB，worker RSS 采样阈值 3 GiB。RSS 含 Lean 加载/编译环境，不是算法空间成本；采样不是瞬时硬上限。

- 1,024：三个形态的 45 个主变体全部完成。
- 4,096：30 个直接变体全部完成；旧解释器 3 个完成、12 个请求超时。
- 16,384：random/sorted 上 20 个直接变体完成，10 个旧解释器请求超时。随后触及总预算，skewed_runs 的全部 15 个变体均未执行。
- 合计 **98 个完成、22 个请求超时、15 个因总预算未执行**，都保留记录。没有把超时记成 5 秒、没有从失败项推断速度倍数；无栈/RSS 失败记录。

只有 1,024 存在全部 15 变体完成的共同输入集合。`extension-pairing-explicit.json` 对其余规模明确保存 null；自动分析中空集合的求和 0 不是零耗时观测。超时请求在进程被终止前尚未返回的部分轮时长无法恢复，不计入完整观测；这是扩展日志粒度的剩余限制。

初设 1 GiB 的两次 smoke 在任何输入计时前被 Lean 启动内存触发；本机 24 GiB，之后统一改成 3 GiB。另一次 smoke 被编译审计的常量名称误报拦住。失败目录保留；最终 smoke 和完整确认使用同一份源码与修订后参数，没有拿确认集调整预算。

## 7. 尚未验证的解释与下一项假设

已证实的是执行器替换收益和上述端到端差异，**尚未分别测得闭包分配、引用计数、列表遍历及规划器各自的机器成本**。

最值得单独检验的具体假设：直接执行后，长度规划器反复 `runs.map List.length`、求和和切分的元数据工作成为明显成本。源码支持这是候选因素，但本轮没有单独识别其因果份额；合并树差异也可能影响执行。

下一实验可以缓存带 `len = data.length` 证据的 run 长度，先证明新旧规划器产生**完全同一棵树**，再只替换元数据表示做配对消融。它不需要改变排序决策或引入 Array。本轮未实现这项优化，也未调参重跑确认集。
